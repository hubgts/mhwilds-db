# Loading into PostgreSQL

```bash
createdb mhw
psql -v ON_ERROR_STOP=1 -d mhw -f schema/postgres.sql      # 116 tables
psql -v ON_ERROR_STOP=1 -d mhw -f schema/load.sql          # 250,000 rows
psql -v ON_ERROR_STOP=1 -d mhw -f schema/constraints.sql   # keys and indexes
psql -v ON_ERROR_STOP=1 -d mhw -f schema/views.sql         # 8 views
```

Verified end to end on PostgreSQL 14. The load takes about a second and a half.

All four files are generated by `scripts/schema.py` from `data/` itself, so the
schema cannot drift from the JSON. Column types are inferred from the actual
values; keys come from the same declarations `check_output.py` enforces.

**Constraints are applied third on purpose.** Creating a foreign key on a
populated table makes PostgreSQL check every row, so that command is the proof
that the dataset is internally consistent, not just plumbing. If it passes, the
250,000 rows hold together.

## Layout

One PostgreSQL schema per `data/` folder, so the SQL reads like the file tree:

```sql
core.items          monsters.drops        weapons.tree_nodes
armor.series        charms.decorations    palico.recipes
world.gimmicks      economy.npc_trades    progression.missions
i18n.translations   views.sheets
```

## Modelling choices

Made once in `scripts/schema.py`, applied uniformly:

**A surrogate `row_id` on every table.** Several files have no natural key:
`weapons` merges 14 sheets and is keyed by the pair `(weapon_type, id)`. Natural
keys still get `UNIQUE` constraints, which is what the foreign keys target.

It is called `row_id` and not `id` on purpose. Several entities carry a field of
their own called `id` — weapons, medals, name plates — and taking that name for
the row number would rename theirs and invite joins on the wrong column. In
`weapons.weapons`, `id` is the game's weapon id and `row_id` is the row number.

**An array of objects becomes a child table, not JSONB.** Those are real
relations: recipe materials point at items and deserve a foreign key.

```sql
weapons.recipes              -- one row per recipe
weapons.recipes_materials    -- recipes_row_id, position, item_data_id, quantity
```

**An array of scalars also becomes a child table**, so `WHERE value = ...` is an
index lookup rather than a containment operator.

```sql
monsters.monsters_locales    -- monsters_row_id, position, value
```

**An object with fixed keys is flattened into columns**, because it is a record,
not a relation: sharpness has seven colours and always will.

```sql
weapons.weapons.sharpness_red, sharpness_orange, ...
```

**Translations are a long table**, `i18n.translations(guid, lang, text)`, with
entities holding GUID references. A column per language would need a migration
every time a language is added.

**SQL reserved words get a trailing underscore**: `class` becomes `class_`,
`type` becomes `type_`, `index` becomes `index_`. `rank`, `part` and `id` are
not reserved in PostgreSQL and keep their names.

**Five foreign keys are deliberately absent**, replaced by an index and a
comment naming the dangling reference in the source. They are the same five
`check_output.py` reports as known warnings, and PostgreSQL refuses to create
them, which is the correct reaction.

## The views

`schema/views.sql` is hand-written, unlike the tables: it encodes what an
application actually asks for, which introspection cannot guess.

| View | Answers |
|---|---|
| `core.items_localised` | every item in every language |
| `monsters.monsters_localised` | every monster in every language, with its icon |
| `monsters.drops_detailed` | reward tables with monster and item spelled out |
| `monsters.item_sources` | where to farm a given item |
| `weapons.weapons_in_tree` | a weapon with its lineage and tier |
| `weapons.upgrade_edges` | the upgrade graph as edges, ready to walk |
| `armor.pieces_with_series` | armour pieces joined to their series |
| `economy.item_demand` | everything that consumes an item, all crafting systems |

### The cardinality assertions

`views.sql` ends with a `DO` block that checks each view returns the number of
rows it should, and raises if not.

Nothing else covers these views. `check_output.py` validates `data/`, and the
foreign keys validate the tables, but a view is hand-written SQL: a join on the
wrong column silently returns fewer rows instead of failing. That is how
`upgrade_edges` once returned 71 rows instead of 957, joining a surrogate key
against a game id.

Each expectation is expressed from a different angle than the view it guards,
so a typo cannot satisfy both. `upgrade_edges` must match the row count of
`weapons.tree_nodes_next_weapon_ids`, `drops_detailed` that of `monsters.drops`,
`item_demand` the sum of the four materials tables, and so on.

On success the block prints `all 8 views return the expected number of rows`.
On failure `psql` stops with the view name, the count it got and the count it
expected:

```
ERROR: view cardinality check failed: weapons.upgrade_edges: 71 rows, expected 957;
```

## Example queries

```sql
-- A weapon's materials, named in French
SELECT tn.text AS material, m.quantity
FROM weapons.recipes r
JOIN weapons.recipes_materials m ON m.recipes_row_id = r.row_id
JOIN core.items i ON i.data_id = m.item_data_id
JOIN i18n.translations tn ON tn.guid = i.name_guid AND tn.lang = 'french'
WHERE r.weapon_name = 'Red Wing I';
```

```
      material       | quantity
---------------------+----------
 Symbole de Chasseur |        5
 Écaille Rathian +   |        5
 Rubis Rathian       |        1
```

```sql
-- Walk one lineage of the Great Sword tree
SELECT from_name, from_tier, to_name
FROM weapons.upgrade_edges
WHERE weapon_type = 'Great Sword' AND lineage = 'Ore Tree'
ORDER BY from_tier;
```

```sql
-- Everything that needs a Rathian Ruby, across all crafting systems
SELECT kind, product, quantity
FROM economy.item_demand
WHERE item_name = 'Rathian Ruby';
```

```sql
-- Rathian's hitzones
SELECT h.slash, h.blow, h.shot, h.fire, h.thunder, h.ice, h.dragon
FROM monsters.hitzones h
JOIN monsters.monsters m ON m.em_id = h.em_id
WHERE m.name = 'Rathian';
```

## Reloading after a game update

```bash
scripts/pipeline.sh --fetch
dropdb mhw && createdb mhw
# then the four psql commands again
```

The CSVs are regenerated into `build/<date>/sql/`, and `schema/load.sql` points
at them by absolute path, so it has to be regenerated too. Stage 6 does both.

For an incremental update instead of a reload, use
`scripts/diff_data.py` to see exactly which records moved, then write the
`UPDATE` statements you need. There is no migration generator; at this data
size a reload is usually simpler.

## Other databases

Nothing in the model is PostgreSQL specific except the schema-per-folder layout
and the reserved-word list. For SQLite, flatten `schema.table` to
`schema_table` and drop the `CREATE SCHEMA` lines. The CSVs load with `.import`
unchanged.
